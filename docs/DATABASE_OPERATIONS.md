# 데이터베이스 운영 원칙

작성일: 2026-09-08

## 기준

- PostgreSQL이 콘텐츠, 투표, 신고, 운영 이력의 유일한 기준 저장소입니다.
- `src/lib/db/schema.ts`가 코드 스키마의 원본이고 `drizzle/`의 SQL은 배포 이력입니다.
- 이미 공유되거나 운영에 적용된 마이그레이션 파일은 수정하지 않습니다.
- `drizzle-kit push`는 운영 환경에서 사용하지 않습니다.
- 모든 변경은 새 순방향 마이그레이션으로 보정합니다.

## 로컬 준비

1. `.env.example`을 `.env.local`로 복사합니다.
2. 별도의 개발용 PostgreSQL 데이터베이스를 준비합니다.
3. `DATABASE_URL`을 개발 DB 주소로 설정합니다.
4. `npm run db:migrate`를 실행합니다.
5. `npm run db:seed`를 실행합니다.

개발 시드는 고정 ID와 `ON CONFLICT`를 사용하므로 반복 적용할 수 있습니다. 외부 이미지나 권리 미확인 자료는 포함하지 않습니다.

## 스키마 변경

1. `src/lib/db/schema.ts`를 수정합니다.
2. `npm run db:generate -- --name=<변경명>`으로 새 SQL을 생성합니다.
3. 생성 SQL에서 잠금, 데이터 손실, 기본값, 인덱스 비용을 검토합니다.
4. `npm run db:check`로 이력 충돌을 검사합니다.
5. 빈 PGlite 데이터베이스에 전체 이력과 시드를 적용하는 테스트를 실행합니다.
6. 실제 PostgreSQL 스테이징 복제본에서 실행 시간과 데이터를 대조합니다.

## 잘못된 마이그레이션 보정

운영에 적용되지 않았다면 해당 변경을 버리고 스키마에서 다시 생성할 수 있습니다. 운영 또는 공유 환경에 한 번이라도 적용됐다면 기존 파일을 고치거나 down migration을 실행하지 않습니다.

대신 다음 순서로 처리합니다.

1. 영향을 받는 행과 쿼리를 읽기 전용으로 확인합니다.
2. 변경 직전 백업과 복원 가능 여부를 확인합니다.
3. 문제를 교정하는 새 순방향 마이그레이션을 작성합니다.
4. 필요한 데이터 변환을 작은 배치와 재실행 가능한 조건으로 작성합니다.
5. 스테이징에서 전후 건수와 무결성 쿼리를 비교합니다.
6. 운영 적용 후 오류율, 지연 시간, 제약 위반을 관찰합니다.

## 백업과 복원

- 배포 전 공급자 스냅샷 또는 `pg_dump` 백업을 생성합니다.
- 백업 파일은 애플리케이션 저장소와 분리하고 암호화합니다.
- 분기마다 별도 데이터베이스에 복원 연습을 수행합니다.
- 복원 검증에는 테이블 건수, 최근 발행 콘텐츠, 투표 원본과 집계 대조가 포함됩니다.
- 연결 문자열과 백업 위치는 로그나 문서 저장소에 기록하지 않습니다.

## 출시 전 확인

- 마이그레이션 이력 충돌 없음
- 빈 DB 전체 적용 성공
- 개발 시드 2회 적용 시 중복 없음
- 공개 상태 열거형과 투표 중복 키 제약 동작
- 후보가 속하지 않은 콘텐츠의 투표 거부
- 원본 투표를 삭제하지 않고 집계 재생성 가능
- 백업 생성과 실제 복원 확인
