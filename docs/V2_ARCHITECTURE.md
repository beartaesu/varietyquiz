# V2 기술 구조

상태: 제안 승인 기준선
작성일: 2026-09-08

## 1. 기술 결정

V2는 **Next.js App Router + TypeScript + PostgreSQL**로 구축합니다.

V1의 Vite SPA를 유지하면 콘텐츠별 서버 HTML, 동적 메타데이터, 사이트맵, 캐시 무효화, 공유 카드 구현을 여러 별도 장치로 보완해야 합니다. Next.js는 V2의 핵심인 공개 콘텐츠 페이지와 참여형 클라이언트 UI를 한 프로젝트 안에서 분리하기에 적합합니다.

정확한 패키지 버전은 실제 기반 작업을 시작할 때 지원 중인 안정 버전을 확인한 뒤 잠급니다.

## 2. 구성

| 계층 | 선택 | 책임 |
| --- | --- | --- |
| 웹 | Next.js App Router, React, TypeScript | 서버 렌더링, 메타데이터, 참여 UI |
| 스타일 | Tailwind CSS | 모바일 우선 UI와 디자인 토큰 |
| 데이터 | PostgreSQL | 콘텐츠, 투표, 집계, 운영 이력 |
| ORM | Drizzle ORM | 타입 안전 스키마와 SQL 마이그레이션 |
| 검증 | Zod | 폼·API 경계 검증 |
| 인증 | Auth.js 계열 어댑터 + 관리자 허용 목록 | P0 관리자 접근 |
| 이미지 | S3 호환 객체 저장소 + CDN | 원본/변환 이미지 저장 |
| 분석 | 공급자 교체 가능한 이벤트 어댑터 | 유입과 참여 퍼널 |
| 오류 | 서버·브라우저 오류 수집 어댑터 | 운영 가시성 |
| 캐시 | Next.js 데이터 캐시, 필요 시 Redis | 공개 읽기 성능 |

Redis는 P0 필수 의존성이 아닙니다. 실제 부하가 PostgreSQL 집계와 애플리케이션 속도 제한으로 감당되지 않을 때 추가합니다.

페이지는 저장소에 직접 접근하지 않습니다. `repository → service → route/server action → UI` 경계를 유지해 집계와 검증 규칙을 한 곳에 둡니다.

## 4. URL 설계

| 경로 | 역할 | 색인 |
| --- | --- | --- |
| `/` | 인기·신규·카테고리 홈 | 허용 |
| `/vs/[slug]` | 설명과 VS 참여 | 허용 |
| `/worldcup/[slug]` | 설명과 월드컵 시작 | 허용 |
| `/worldcup/[slug]/play` | 진행 전용 | 기본 차단 |
| `/result/[slug]` | 누적 결과와 해설 | 허용 |
| `/rankings` | 전체/기간/분류 랭킹 | 허용 |
| `/categories/[slug]` | 카테고리 허브 | 허용 |
| `/tags/[slug]` | 태그 허브 | 품질 기준 충족 시 허용 |
| `/search` | 검색 결과 | 기본 차단 |
| `/about`, `/contact`, `/privacy`, `/terms` | 신뢰·정책 | 허용 |
| `/admin/*` | 운영 화면 | 차단·인증 필수 |

진행, 로그인, 알림, 이동, 빈 검색 결과 같은 행동 중심 화면에는 광고 슬롯을 렌더링하지 않습니다.

## 5. 핵심 데이터 규칙

### 콘텐츠 상태

`draft → review → published → hidden → archived` 흐름을 사용합니다. `published`만 공개 조회에 노출하며, 상태 변경은 감사 로그에 남깁니다.

### 익명 투표

- 브라우저에는 무작위 세션 토큰을 서명 쿠키로 저장합니다.
- DB에는 원문 토큰이 아니라 회전 가능한 서버 비밀로 만든 해시만 저장합니다.
- 콘텐츠와 대결 단위의 유일 키로 단순 중복을 차단합니다.
- IP 원문은 저장하지 않고, 필요 시 짧은 보존 기간의 위험도 키만 사용합니다.
- 속도 제한과 비정상 패턴 플래그는 투표 집계와 분리합니다.
- 중복 방지는 완전한 신원 증명이 아니라 남용 완화로 명시합니다.

### 집계

원본 `vote`가 진실의 원천입니다. `content_stats`와 `candidate_stats`는 읽기 성능을 위한 파생 데이터이며 재계산할 수 있어야 합니다. 투표 기록과 집계 갱신은 한 트랜잭션에서 처리합니다.

## 6. 렌더링·SEO

- 홈, 상세, 결과, 랭킹, 카테고리는 서버에서 의미 있는 초기 HTML을 생성합니다.
- 발행 콘텐츠별 title, description, canonical, Open Graph, JSON-LD를 생성합니다.
- 사이트맵은 발행 상태와 수정 시각을 DB에서 읽어 생성합니다.
- `robots.txt`에서 관리자, 검색 결과, 플레이 전용 경로를 제한합니다.
- 삭제 콘텐츠는 상태에 따라 404 또는 410을 일관되게 반환합니다.
- 참여 UI만 클라이언트 컴포넌트로 두고 설명·결과는 서버 컴포넌트를 우선합니다.

## 7. 이미지·저작권

- 사용자가 임의 URL을 서버 프록시로 가져오게 하지 않습니다.
- 관리자가 허용된 형식과 크기의 파일을 직접 업로드하도록 합니다.
- MIME 확인, 디코딩 검사, 크기 제한, 파일명 재생성, 메타데이터 제거를 적용합니다.
- 후보마다 대체 텍스트, 출처 URL, 권리 상태, 검수자를 기록합니다.
- 권리 상태가 확인되지 않은 이미지는 발행할 수 없게 합니다.

## 8. 광고·동의 경계

광고는 `AdSlot` 한 컴포넌트와 서버 측 페이지 정책으로만 노출합니다. 개별 페이지가 광고 코드를 직접 삽입할 수 없게 합니다.

광고 허용 조건은 다음을 모두 만족해야 합니다.

1. 발행된 공개 콘텐츠 또는 충분한 고유 설명이 있는 허브다.
2. 빈 상태, 진행 전용, 이동, 알림, 오류 화면이 아니다.
3. 운영자가 광고 허용 상태로 검수했다.
4. 해당 지역에서 필요한 동의 상태가 충족됐다.
5. 광고가 선택 버튼이나 주요 행동과 혼동되지 않는 위치다.

초기 P0에서는 광고 컴포넌트를 기본 비활성화하고 콘텐츠·동의·측정 검증 후 별도 출시 게이트로 켭니다.

## 9. 보안 기준

- 모든 변경 API에 서버 측 인증·인가와 Zod 검증을 적용합니다.
- 관리자 쓰기 작업은 CSRF 방어와 감사 로그를 갖춥니다.
- 투표, 검색, 로그인, 업로드에 서로 다른 속도 제한을 둡니다.
- 비밀값은 환경 변수 저장소에서만 관리하고 로그에 남기지 않습니다.
- 외부 URL fetch는 기본 금지하며 필요한 공급자 호출은 고정 호스트만 허용합니다.
- 의존성, 정적 분석, 타입 검사, 테스트를 CI 필수 단계로 둡니다.

## 10. 테스트 전략

- 단위: 토너먼트 전이, 집계, 공개 상태, 슬러그, 광고 허용 규칙
- 속성 기반: 16/32강에서 모든 후보가 정확히 한 경로로 종료되는지 검증
- 통합: 투표 트랜잭션, 중복 키, 집계 재계산, CMS 상태 전이
- E2E: 홈→상세→참여→결과→공유, 관리자 작성→발행→숨김
- SEO: 서버 HTML 메타데이터, canonical, 사이트맵, robots, 404/410
- 접근성: 키보드 선택, 포커스 이동, 대비, 이미지 대체 텍스트
